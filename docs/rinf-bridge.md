# rinf bridge

How the Rust core, the rinf bridge, and the Flutter GUI fit together.
rinf is a **separate layer**: the core does not know it exists, and Flutter
only knows the signals it defines.

## Layers

```
native/core   (jitter_core)    business logic + state. No rinf, no tokio, no I/O.
      ▲
native/twitch (jitter_twitch)  Twitch access: responses ↔ core types.
native/store  (jitter_store)   SQLite: implements core's storage ports.
      ▲                ▲
native/hub    (hub)   native/cli  (jitter_cli)
  rinf bridge           CLI head
      ▲
lib/src/bindings      generated by `rinf gen` from native/hub/src/signals
      ▲
lib/                  Flutter GUI: view state, widgets, platform effects
```

Dependencies point down the arrows only.

> The code examples below come from coffee_timer, where this layering was
> first built (recipes, brews, a SQLite store). The rules carry over; the
> names do not — read `coffee_timer` as the reference shape, not jitter's API.

- **core** decides. It exposes feature controllers: actions in, state and
  effects out. It defines the infrastructure traits it needs (`ports/`) and
  implements them only as test fakes (`fakes/`, behind `test-fakes`).
- **twitch** talks to Twitch. It returns core types, turning Twitch's APIs,
  playlists and chat wire formats into them. Core never calls twitch; heads
  ask core what to load, call twitch, and hand the result back. Storage
  enters through core's ports. No decisions; no rinf.
- **store** persists. `SqliteStore` implements core's storage ports
  (`FavoritesStore`, `ResumeStore`) over one SQLite file that every head on
  the machine shares: WAL, migrations in an `IMMEDIATE` transaction, and no
  upsert that could bring back a row another process removed. No decisions;
  no rinf.
- **hub** translates. It builds the controllers with their infrastructure,
  turns Dart signals into controller actions, owns the tick interval, signals
  platform effects to Dart, and turns controller state into Rust signals. It
  holds no business `if`.
- **cli** is a second head on the same core and twitch crates. It is the proof that the
  core does not need rinf; if the CLI cannot do something without Flutter,
  logic leaked into the hub or Dart.
- **Flutter** renders and performs platform effects (sound, vibration,
  wakelock) when told to. It folds incoming changes into view state and sends
  user intents. It holds no business `if`.

## The core API

The core is a set of **feature controllers**, each owning one state object.
An action takes plain values, mutates the state, and returns only what state
cannot hold (one-shot effects, or a `CatalogChange`). Tests run an action and
assert the state.

```rust
// native/core (fields abridged)
pub struct RecipeCatalog { state: Vec<Recipe>, store: Box<dyn RecipeStore> }
pub struct EditorController { state: EditorState, ids: Box<dyn IdGen> }
pub struct BrewController { state: BrewState }

impl EditorController {
    pub fn save(&mut self, catalog: &mut RecipeCatalog) -> Result<CatalogChange, SaveError>;
}
impl BrewController {
    pub fn start(&mut self, from: usize) -> Result<Vec<Effect>, BrewError>;
    pub fn tick(&mut self) -> Vec<Effect>;
    pub fn state(&self) -> &BrewState;
}
```

Two ways in, one rule for choosing:

| Dependency | Enters through | Why |
|---|---|---|
| Infrastructure: `RecipeStore`, `SettingsStore`, `IdGen` (jitter: `FavoritesStore`, `ResumeStore`) | constructor (`Box<dyn Trait>`) | Border dependency; traits live in core, real impls in `store` (`SqliteStore`, `UuidIds`; jitter: `jitter_store::SqliteStore`, one clone per controller), fakes in core's `fakes/` |
| Shared controller: `RecipeCatalog` | method argument (`&` / `&mut`) | Shared mutable state; the borrow checker proves who reads and who writes, with no `Rc<RefCell>` and no runtime borrow failures |

- The controller that owns data owns its persistence: `RecipeCatalog`
  writes through its store before updating its state; `SettingsController`
  likewise. A failed write leaves the state unchanged and returns `Err`.
- No coordinator object owns the features; a flow belongs to the controller
  of the feature that starts it.
- Core types do not derive `RustSignal`/`DartSignal` — the core does not
  depend on rinf.
- No controller reads the clock: the timer counts the ticks it is given.
- An `Effect` is a decision already made, for the shell to carry out:
  `PlayStepSound`, `Vibrate { ms }`, `VibratePattern { pattern_ms }`,
  `KeepScreenOn(bool)`,
  `ShowBrewNotification(BrewNotice)`, `HideBrewNotification`.
- A `CatalogChange` (`Upserted` / `Removed`) is already persisted when it is
  returned. The shell passes it on unconditionally: send it as a list diff,
  hand it to `BrewController::on_catalog_change`.
- `RecipeCatalog::load` returns no change (`Result<(), StoreError>`); it
  runs once at boot, and the list snapshot is read from `state()`.

### The timer

`BrewController` holds the timer as a state machine (idle / running at step
*n* with *s* seconds left). It never sleeps or schedules. The hub creates a
`tokio::time::interval` when a brew starts, drops it when the brew ends, and
calls `tick` on each beat. "Advance at zero, finish after the last step"
lives in the controller and nowhere else.

## The hub

```
native/hub/src/
  lib.rs              starts the runtime, opens the store, spawns the hub task
  signals/
    mod.rs
    <feature>.rs      the signal types for one feature
  run.rs              the hub task: owns the controllers, one select! loop
  <feature>.rs        controller state ↔ signal mapping for one feature
```

### Signals are the Dart contract

- Signal structs live only in `native/hub/src/signals/`, one file per
  feature. They are DTOs shaped for the GUI, not core types re-exported.
- Mapping is `From`/`Into` between core types and signal types, in the hub.
  Pure, no decisions — if a mapping needs an `if` on business meaning, the
  controller should have returned a different state, `Effect`, or change.
- Run `rinf gen` after any change in `signals/`. Generated Dart is
  gitignored, so also run it on a fresh checkout before `flutter analyze`.

### Inbound: one listener per Dart signal

rinf keeps **one active receiver per `DartSignal` type**; calling
`get_dart_signal_receiver()` again silently deactivates the earlier one.
So each inbound signal has exactly one listener loop, in the hub task that
owns the feature. Signals sent before the loop starts are queued, not lost.

```rust
// native/hub/src/run.rs  (shape, not final code)
loop {
    tokio::select! {
        Some(pack) = start_brew.recv() => {
            let effects = brew.start(pack.message.from)?;
            BrewUpdate::from(brew.state()).send_signal_to_dart();
            perform(effects);
        }
        Some(_) = next_tick(&mut interval) => { /* brew.tick() … */ }
        // … one arm per Dart signal
    }
}
```

One hub task owns every controller, so actions run one at a time and need
no locking. All inbound signal types are merged with `tokio::select!` rather
than sharing controllers across tasks.

### Outbound: one enum signal per feature

Each feature sends **one** `RustSignal` type for view state. Brew, editor,
and settings send their **whole view state** after every action (a few
hundred bytes); Dart replaces it. The recipe list is a keyed collection that
can grow, so it sends a snapshot (`RecipeListUpdate::snapshot`, from
`RecipeCatalog::state()`) and then diffs. Each diff is built from a
`CatalogChange` and the catalog (`RecipeListUpdate::of`): the changed row
as the catalog now holds it, or `Removed` when it holds no such id.

```rust
#[derive(Serialize, RustSignal)]
pub enum RecipeListUpdate {
    Snapshot { recipes: Vec<RecipeSummary> },
    Upserted { recipe: RecipeSummary, index: u32 },
    Removed { id: String, undo_notice: Option<String> },
    Failed { message: String },
    Notice { message: String },
}
```

`Upserted` places the row: Dart drops any row with its id, then inserts it
at `index` (list order). An edit keeps the index, and a pin or unpin moves
it.

`Failed` is a one-shot notice, not state: a list delete (`RemoveRecipe`),
an undo (`UndoRemoveRecipe`), a pin (`PinRecipe` / `UnpinRecipe`), a
ratio save (`SaveBrewRatio`), an export (`ExportRecipes`) or an import
(`ImportRecipes`) failed, the list is unchanged, and Dart shows
`message` (core's `DeleteError`, `RestoreError`, `PinError`,
`SaveRatioError`, `ExportError` or `ImportError` text) as a snackbar
each time one arrives. `Notice { message }` is the same for an export's
or import's success (`Copied 2 recipes`). `Removed`'s `undo_notice` is one-shot the same way:
present when core offers to undo that removal, shown once as a snackbar
with an Undo.

One type means one Dart stream, so a snapshot and the diffs after it
arrive in order. Splitting them across signal types gives up that ordering.

Platform effects go on their own signal, `PlatformEffect` (an enum:
`PlayStepSound`, `Vibrate`, `VibratePattern`, `KeepScreenOn { on }`,
`ShowBrewNotification { title, next }`, `HideBrewNotification`,
`CopyToClipboard { text }`). They are
commands, not state: Dart performs them and keeps nothing.

### Snapshot handshake

On the Dart side, each Rust signal type is a broadcast stream that buffers
only until its **first** listener. Anything a later listener needs from
before it subscribed is gone, and `latestRustSignal` holds a single message
— useless for diffs.

So every feature has a ready signal:

1. Dart creates the feature's view-state holder, subscribes to its update
   stream, then sends `<Feature>Ready`.
2. The hub answers with the feature's current state (`Snapshot` for the
   recipe list), read from the owning controller.
3. Every update after that is a new state, or a list diff.

This also covers Flutter hot restart, where Dart state resets but Rust keeps
running.

### Startup

Rust cannot find the app's documents directory on every platform by itself.
Dart resolves it (`path_provider`) and sends it once in a `Boot` signal; the
hub opens and migrates the store at that path, loads recipes and
settings into the controllers, and only then starts the hub task. If that
fails it sends `BootFailed { message }` and waits for another `Boot`; Dart
shows the message with a Retry that resends `Boot`. Until both the first
recipe-list snapshot and the settings arrive the GUI shows a spinner.

**jitter deviates on desktop.** Its database is shared by the GUI and the
CLI, so the location is defined once, in Rust: `jitter_store::default_db_path()`
(`<platform data dir>/jitter/jitter.db`). The desktop hub opens that and
ignores any directory in `Boot`; `path_provider` would give a different,
app-id-named directory, and copying its per-platform rule into the CLI would
put the path in two languages. On Android/iOS there is no CLI and the
sandbox requires Dart's directory, so `Boot`'s directory is used there.

## Flutter

- One view-state holder per feature (e.g. a `ChangeNotifier`), created at
  app start and kept for the app's lifetime. It subscribes with
  `rustSignalStream.listen` — not `StreamBuilder`, which may skip messages
  that arrive within one frame and would drop diffs and timer ticks.
- Applying an update is mechanical: a state or `Snapshot` replaces; list
  diffs insert / update / remove by id. A value the GUI needs but cannot
  derive mechanically (a `M:SS` label, grams, total duration, step status)
  is computed in Rust and sent.
- One `PlatformEffect` listener calls `audioplayers`, `vibration`, and
  `wakelock_plus`. It maps each variant to one plugin call, no conditions.
- Widgets read holders and send intents (`StartBrew(...).sendSignalToRust()`).
  Leaving the timer page is an intent too (`LeaveBrew`); Rust decides that
  the wakelock goes off.
- Widgets do not listen to signal streams directly.
- On app exit call `finalizeRust()` from an `AppLifecycleListener` so Rust
  can close the database.
- Theme rendering is Flutter's; the theme *setting* is Rust state like any
  other and arrives as a settings snapshot.

## Testing

| Layer | How | Gate |
|---|---|---|
| core | run an action, assert the controller state (timer tick by tick); fake stores and ids | `cargo test` |
| twitch | parse recorded responses into core types | `cargo test` |
| hub mapping | unit test a `From` impl only when it is non-trivial | `cargo test` |
| hub loops | not unit tested — kept thin enough to read | `cargo clippy --all-targets` |
| core end-to-end | drive it from the CLI | `cargo run -p jitter_cli` |
| Dart folding | unit test holders with hand-built signal values | `flutter test` |

## rinf gotchas

- `rinf gen --watch` is broken (rinf #682); run `rinf gen` by hand.
- `#[serde(with = ...)]` is rejected on signals; convert in the `From` impl.
- Recursive signal types need `Option<Box<T>>`.
- 64-bit integers lose precision on the web target. Ids are UUID strings
  already; keep timestamps within 2^53 or send them as `String` if the web
  head is ever built.
- No panics in the hub or core: a panic on the web target cannot be caught
  and leaves Dart waiting forever. Return `Result`, and report errors in
  the hub before they would cross the boundary.
